# V0.4 responsive widgets and platform notes

## Implemented decisions

- A one-column calendar uses a compact toolbar that keeps Today, previous/next, current time, search, Day/Week and close controls available. The calendar-source panel is collapsed when the widget becomes narrow and reopens as an overlay, so it no longer consumes a permanent content column.
- Weather requests include Open-Meteo's closest hourly history (`past_hours=24`). The header Rain History button cycles past 1 hour, past 24 hours and the regular forecast. Totals and bars are based on hourly precipitation; this is model data, not a physical rain gauge.
- Every widget has a release-time `VITE_FEATURE_WIDGET_*` flag. Disabled widgets are removed from normalized saved layouts, the rail and their Settings section. Codex defaults to disabled.
- Responsive UI coverage lives in `tests/responsive-widget-smoke.mjs` and exercises 1280×480 and 1920×720 layouts, one-column calendar controls, the calendar-source overlay, rainfall history, and Codex release exclusion.

## Microsoft Teams widget feasibility

This is a high-complexity integration, not a small dashboard card. The existing Microsoft PKCE sign-in is a useful base, but the Entra registration would need delegated Microsoft Graph chat/message scopes and tenant consent. A usable first version needs chat discovery, paging, message rendering, send/edit flows, token renewal, permission/error states and throttling handling. Images can use Teams hosted content; normal files are stored in SharePoint or OneDrive and need a separate upload/download flow. Near-real-time sync needs Graph change-notification subscriptions and a public HTTPS callback service with subscription renewal.

A read/send MVP for one work-or-school tenant is roughly 4–8 engineering weeks. A polished Teams-like experience with group chats, rich composition, mentions, images/files, edits, unread state, resilient background sync and multi-tenant administration is more realistically 2–4+ months, plus ongoing Graph compatibility and security work.

## Display persistence and kiosk behaviour

Normal application mode should save a preferred monitor identity and reapply its physical bounds/fullscreen state at launch, resume, unlock and display-change events. Tauri exposes monitor enumeration plus position, size, fullscreen and always-on-top controls. On Windows, a native layer can additionally react to `WM_DISPLAYCHANGE`; on macOS it can react to `NSApplicationDidChangeScreenParametersNotification`.

Always-on-top is optional and should not be the default: it keeps the dashboard above ordinary windows but also prevents normal overlap until explicitly disabled. A normal desktop application cannot guarantee that no other application ever covers it. That guarantee requires managed kiosk configuration: Windows Assigned Access or Shell Launcher for a dedicated device, and an equivalent managed single-app/kiosk policy on macOS.

For a Windows 11 laptop undocking, the app should detect the target monitor disappearing, remember its identity and intended bounds, move to or minimize on the internal display according to a user-selected fallback, then restore to the external monitor when it returns. Windows 11's “Remember window locations based on monitor connection” and “Minimize windows when a monitor is disconnected” settings complement this app-level handling but should not be the only mechanism.
